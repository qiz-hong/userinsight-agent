# Interview Q&A — UserInsight Agent

面试追问备答材料。核心策略：每个"为什么没有 X"都答成"因为场景不需要 X，加了反而有害，但我知道 X 在什么条件下该上"。展现的是工程判断力。

---

## 一、定性类

### Q1. 没有 loop，凭什么叫 Agent？

- 升级后**已有 loop**：Executor ⇄ Critic 反思循环，结果不达标自动回溯重试（清洗-诊断闭环、分群-评估闭环、预测-基线闭环）。
- 严格说属于"结构化 Agent / LLM 增强工作流"，不是完全自主 Agent。Agent 是个谱系。
- 护栏设计：最大迭代轮数 + 每步重试预算，保证循环可控终止——无限 loop 不是优点，是事故。
- 延伸：知道什么场景该上完全开放式 loop（任务本身不确定、需要多轮探索），数据分析不是。

### Q2. 去掉 LLM 还能跑吗？LLM 是不是噱头？

- 能跑。每个 LLM 节点都有确定性回退：Planner 回退静态计划、Executor 直接按计划调工具、Critic 回退规则判断。
- LLM 是"决策增强层"不是"依赖层"：拔掉它系统还活着，只是"没那么聪明"。

### Q3. 为什么不用 LangChain 全套，只用了 LangGraph + 工具？

- LangGraph 只负责编排（状态图、循环、条件边），这是我需要的全部。
- 不自造 LLM SDK：用 langchain-openai 接 DeepSeek（OpenAI 兼容），任何兼容端点/本地模型可切换（LLM_BASE_URL 环境变量）。

### Q4. RAG 和记忆区？

- **有记忆**：ChromaDB 向量库存历史 schema、有效策略、业务结论，Planner 规划时召回作为上下文。
- **不需要 RAG**：分析型 Agent 的知识就在用户上传的数据里，外部知识检索是对话型 Agent 的需求。强行加 RAG 是堆技术。

## 二、可靠性类

### Q5. LLM 输出 JSON 解析失败 / 给了非法参数怎么办？

三层防护：
1. `_extract_json` 兼容裸 JSON / markdown 代码块 / 文本中提取；
2. 每个 LLM 节点 try/except，失败回退确定性路径；
3. 工具层 `_safe_run` 参数校验（TypeError 回退空参、任何异常返回 ERROR 字符串供 Critic 决策）。

架构思想：**LLM 给建议 + 确定性兜底**。LLM 不稳定，但系统结果稳定。

### Q6. 同样数据跑两次结果不一致？

- 数据处理、特征、聚类（seed=42）、模型（seed=42）完全可复现。
- LLM 决策层有轻微不确定性（模型固有），但影响被隔离在"策略选择"层面，且有关键校验兜底。

### Q7. LLM 幻觉导致特征重要性被误读？

特征重要性来自模型（RF/GBDT 的 feature_importances_ / LR 系数），是数学量不是 LLM 生成的，不存在幻觉。LLM 只做“数字→业务语言”的翻译，底层数据是硬的。

## 三、成本 / 延迟 / 隐私

### Q8. LLM 成本与延迟？

- 3-4 次 LLM 调用 × max_tokens 1024，DeepSeek 定价下单次分析 < 0.05 元。
- 延迟增加约 5-10 秒（规划/反思/总结串行，有依赖无法全并行）。

### Q9. 数据传给 DeepSeek，隐私合规？

- LLM_BASE_URL 可配，可一键切本地部署模型（Ollama/vLLM），数据不出内网。
- 传给 LLM 的只是列摘要 + 少量样本，不是全量数据。
- 列名做了注入风险字符清洗。

---

## 四、数据边界

### Q10. 能处理多大数据？

- 建模链路定位中小规模业务数据（十万~百万行级，取决于内存）：pandas 全量内存 + sklearn。
- **查询链路已用 DuckDB**：列式引擎单机可处理上亿行，自然语言查数工具的数据规模与建模解耦。
- 决策层与执行层解耦：工具层可整体替换为 PySpark/数仓下推（Agent 只写 SQL），架构已预留，大数据需 Spark/数仓——已知边界，可延伸。

### Q11. 缺失率很大能处理吗？

- 中低缺失（<30%）：中位数/众数填充可靠。
- **高缺失（>80%）自动剔除列**（单值填充会注入假信号），这是升级后的策略。
- 常量列、全空列自动剔除；inf 自动转 NaN 再填充。
- 进一步方向：缺失指示列、模型预测填充（保留缺失模式信息）。

### Q12. 乱码 / 异常列名 / 空文件？

- 编码链自适应（utf-8-sig → utf-8 → gbk → gb2312 → latin-1）。
- 列名去空、去重、去特殊字符（同时缓解 prompt 注入）。
- 空文件 / 全空数据给出明确错误而非崩溃。

## 五、价值 / 评估

### Q13. Demo 准确率 1.0，不真实吧？

- 主动坦诚：小样本 + 聚类标签可分性好，准确率虚高，不代表真实性能。
- 代理标签局限：无真 label 时用"最小簇当流失"是演示策略；真实落地接业务真 label（代码支持显式 target_column）。
- 真实评估应做：基线对比、跨数据集验证、业务指标（挽回率）。

### Q14. 和 AutoML（AutoGluon/H2O）的差异？

- AutoML 解决"自动化建模"（搜模型/超参）；本项目解决"端到端业务分析"——脏数据诊断、清洗决策、分群、预测到业务语言报告的全链路，且带语义决策（解释为什么这么分群）。
- 一句话：AutoML 找最优模型，我是替代数据分析师跑完整个分析闭环并写出结论。

---

## 六、面试总纲（背这一句）

> "我的系统是'确定性工具层 + LLM 决策层'的结构化 Agent：Planner 分解任务、Executor 自主调工具、Critic 反思重试。循环有护栏、记忆有 ChromaDB、LLM 有兜底。它的价值不是'像 Agent'，而是'让不懂代码的人也能跑完整个分析闭环并拿到业务结论'。"
